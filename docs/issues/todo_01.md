# Project: tetorica-msfa-dx7-wasm

実装状況（2026-10-15）：Phase 1〜6のMVPを実装。
調査と採用した制約は [research.md](../research.md)、
検証結果と未確認環境は [verification.md](../verification.md)、
利用方法は [README](../../README.md) を参照。

## 目的

Google の music-synthesizer-for-android (msfa) に含まれる
DX7互換FM音源エンジンを WebAssembly に移植する。

TypeScript / JavaScript から DX7 の音色を読み込み、
MIDI Note On/Off によって演奏できるライブラリを作成する。

ブラウザでは AudioWorklet を利用してリアルタイム再生する。

本プロジェクトは Tetorica シリーズの独立した音源ライブラリとする。
既存の Tetorica Playground への統合は今回行わない。

今回はMVPを優先する。
最優先の完成条件は、DX7のSysEx音色を読み込み、
ブラウザ上で鍵盤を押して演奏できること。

実機との完全一致、複数サンプルレートの同時利用、
独自のボイススティーリングは今回の必須条件に含めない。
過度な抽象化や大規模なリファクタリングを避ける。

特に以下を確認する。

## 最初に記録する調査結果と採用した制約

Phase 1に進む前に、次の調査結果とMVPで採用する方針を
リポジトリ内のドキュメントに短く記録する。

- 採用したupstreamのコミットと、利用するソースファイル
- msfaの本来の動作レートと、その根拠となるコードや資料
- 周波数テーブル、LFO、振幅／ピッチエンベロープのレート依存
- global/staticな状態の共有範囲と、初期化による他インスタンスへの影響
- DX7演算コアと、SynthUnitの発音管理・フィルター等の採用範囲
- PCMの出力形式、音量の正規化／クリップ方法
- 発音管理の上流挙動と、MVPで残す制限

内部レートは調査結果に基づき、原則一つに固定する。
MVPでは内部レートの動的変更や、異なる内部レートの同時利用を要求しない。

ブラウザ出力はAudioContextの実際のsampleRateに合わせる。
内部固定レートと異なる場合は出力側でリサンプリングし、
音高と再生速度を維持する。44100 Hz／48000 Hzの出力を検証する。
非対応の出力レートがある場合は、明示的なエラーと制約の説明を付ける。

単一内部レートに制限する場合も、同じレートのインスタンス間で
音色・発音・初期化・破棄が干渉しないことを確認する。

調査だけで作業を終了しない。
採用した制約を記録した後、そのままPhase 1以降の実装を進める。

## Phase 1: WASM化

msfa のDX7音源エンジンを抽出する。

必要なソースファイルと依存関係を特定し、
Emscriptenでコンパイルする。

最低限、以下を実装する。

- 音源インスタンスの生成・破棄
- 音色パラメーターの設定
- Note On
- Note Off
- PCM生成
- 採用した内部固定レートでの動作と、必要な出力側リサンプリング

C++ と JavaScript の境界は薄く保つ。

PCM生成時のメモリコピーをできるだけ抑える。

まず単音のPCMを生成できることを確認する。

発音数は上流の16音制限を維持する。
ボイス割り当ては原則msfaの実装を利用し、
ボイススティーリングの独自実装は行わない。

同音連打、重複したNote Onに対するNote Off、
全16音を使用中の追加発音、音色切り替え中の発音、
All Notes Offの挙動を確認する。
All Notes Offがリリースを伴うのか、即時消音なのかも明記する。
上流の挙動と残る制限はREADMEに記録する。


## Phase 2: DX7音色対応

DX7の音色データを読み込めるようにする。

対応対象：

- DX7 1 Voice SysEx
- DX7 32 Voice Bank SysEx

SysExのヘッダー、データ長、チェックサムを検証する。

音色パラメーターは可能な限り元の値を保持する。

音色データの解析と音源エンジンへの適用を分離する。

音色一覧、音色名、音色選択のAPIを提供する。

第三者の音色バンクは権利を確認せず同梱しない。


## Phase 3: TypeScript API

TypeScriptから簡単に利用できるAPIを作成する。

以下は目標とするAPIのイメージ。
実際のmsfaの構造に合わせて調整してよい。

```typescript
const synth = await createDX7({
  // PCMの出力レート。内部レートは調査結果に基づき固定する。
  sampleRate: 44100,
});

await synth.loadSysex(syxData);

synth.selectVoice(0);

synth.noteOn(60, 100);

const pcm = synth.render(1024);

const buffer = new Float32Array(1024);
synth.renderInto(buffer);

synth.noteOff(60);

synth.allNotesOff();
synth.dispose();
```

PCM出力の契約：

- mono／Float32Arrayを基本とし、値の範囲は原則-1.0〜1.0とする。
- sampleRateは返すPCMの出力レートを表す。内部固定レートとは区別する。
- render(frames)は指定フレーム数の新しい配列を返す。
  返却済み配列は次回のrenderやdisposeで書き換えない。
- renderInto(buffer)は呼び出し側の既存Float32Arrayへ書き込み、
  buffer.lengthフレーム分だけ時間を進める。
- 両APIは同じ音源状態を進める。続けて呼べば続きのPCMを生成する。
- 0フレーム、不正な入力、初期化前・dispose後の呼び出しの扱いを明記する。
- monoという今回の契約を明確にし、将来のstereo対応を妨げない構造にする。
  今回は汎用的な多チャンネル音声フレームワークを作らない。

APIにはTypeScriptの型定義を付ける。

音源コアはDOMやAudioContextに依存させない。

WASMの初期化とインスタンス管理を明確にする。

同期的にPCMを生成するコアAPIと、
AudioWorkletを制御するブラウザ用APIを分離する。


## Phase 4: AudioWorklet

AudioWorkletProcessorでWASM音源を動作させる。

メインスレッドから以下を制御できるようにする。

- 音色の読み込み
- 音色選択
- Note On
- Note Off
- All Notes Off

音声生成はAudioWorklet内で行う。

AudioWorkletのprocess()内では、
不要なメモリ確保を避ける。

バッファは事前に確保し、WASMの初期化や音色解析を
process()内で行わない。音声処理中の不要なWASMメモリ拡張も避ける。

通常の128フレームに対応し、処理長は実際の出力配列から取得する。

音源コアが要求する内部ブロックサイズとの差は
バッファリングで吸収し、余りを次の呼び出しへ保持する。

初期化完了を待てるブラウザ用APIを提供する。
デモでは準備完了まで鍵盤と演奏操作を無効にしてよい。
初期化前のAPI呼び出しは明示的に拒否するなど、扱いを統一する。
MVPのために複雑な初期化前の要求キューを作らない。

音色読み込み、音色選択、Note On／Offの送信順と適用順を保証する。
音色読み込みの完了は、Worklet側で適用できたことを確認して通知する。
読み込み完了直後のNote Onが、指定した音色で鳴ることを保証する。

演奏イベントをどの内部ブロック境界から適用するかを明記する。
サンプル精度の予約スケジューラーの新設は今回の必須条件にしない。

初期化・読み込みの失敗とdisposeを扱い、
破棄した音源の処理が後から再開しないようにする。


## Phase 5: Browser Demo

Viteを使用してブラウザデモを作成する。

最低限のUI：

- Audio Start
- SysExファイル読み込み
- 音色一覧
- 音色選択
- ピアノ鍵盤
- MIDI Note On / Off
- All Notes Off

PCキーボードでも演奏できるようにする。

初期化中・音色読み込み中・演奏可能・失敗の状態を表示する。
初期化中や音色の切り替え中は、鍵盤を無効にする方法でよい。
フォーカスを失った場合や鍵盤操作を終了した場合の音の残留も確認する。

Chrome / Safari / Firefox を対象とする。

実機で確認できない環境については
未検証として記録する。


## Phase 6: Tests

以下を検証する。

1. WASMの初期化と破棄
2. Note OnによるPCM生成
3. Note Off後のエンベロープ減衰
4. 複数音の同時発音
5. SysEx音色データの解析
6. 不正なSysEx入力の処理
7. 同一入力に対するPCM出力の再現性
8. AudioWorkletでの連続再生
9. メモリリークの有無
10. 同じ音色・イベント位置・出力フレーム数で、renderの分割数を変えてもPCMが一致すること
11. renderとrenderIntoの出力一致、返却配列の独立性と保持
12. 採用した内部レート、および44100 Hz／48000 Hz出力での音高と再生速度
13. 同一内部レートの複数インスタンスの非干渉と、異なる内部レートを許可しない制約
14. 初期化完了・音色読み込み完了直後の発音と、Workletへの適用順序
15. 同音連打、同音の重複、16音使用中の追加発音、All Notes Off
16. UI操作中を含むAudioWorkletの連続再生と、内部ブロックの余り処理

msfaのネイティブ版とWASM版で、同じコア・内部レート・音色・
イベント位置・出力経路のPCMを比較する。
差が出る場合は差分の大きさと原因を調べ、比較条件と結果を記録する。

音質の主観的な一致だけでなく、
波形の差も確認する。

DX7実機との完全一致は今回の完成条件に含めない。

テストはPhase 6まで後回しにせず、各Phaseで関連項目を検証する。
実行できない比較や環境がある場合は、その理由を明記する。

## 開発方針

まず調査し、実装可能な最小構成を決める。

調査だけで終了せず、
実装可能ならPhase 1から順次進める。

各Phaseの終了時にビルドとテストを実行する。

既存のmsfaの演算処理は原則変更しない。

必要以上の抽象化を行わない。
MVPに不要な大規模リファクタリングを行わない。

既存のTetoricaパッケージへの依存を作らない。

最初の完成目標は、

「DX7のSysEx音色を読み込み、
 ブラウザで鍵盤を押すと音が鳴る」

こと。

問題は可能な範囲で自律的に解決し、解決できない問題だけ報告する。
必須条件に含まれない完全再現や機能拡張で、MVPの完成を止めない。

作業終了時には以下を報告する。

- 実装した機能
- 動作確認した環境
- 未実装の機能
- 音源エンジンの制約
- upstreamからの変更点
- ライセンス上の注意点
