# MSFA DX7：発音中のパラメーター変更への対応

## 目的

現在のTetoricaのMSFAベースDX7音源では、オペレーターやアルゴリズムの変更が基本的に次のNote Onから反映される。

これを改善し、**YM2612と同様に、Note On後も音色パラメーターをリアルタイムに変更できるようにする。**

Google MSFAをベースとし、Apache-2.0ライセンスを維持する。

## 1. 既存実装の調査

まず、現在のDX7実装を調査する。

確認事項：

- MSFAのソースコードの配置
- Note On時の音色パラメーター初期化処理
- アクティブボイスの管理方法
- オペレーターのエンベロープ状態
- アルゴリズムの保持・更新方法
- WASMとJavaScript間のAPI
- 既存の `setOperator`、`setOperators`、`setPreset` などの実装状況

既存のAPIとの互換性を維持すること。

## 2. 参考実装の調査

以下を調査する。

### Google MSFA

https://github.com/google/music-synthesizer-for-android

元のApache-2.0実装。

### Dexed

https://github.com/asb2m10/dexed

特に以下を確認する。

- `Source/msfa/`
- `Env::update()`
- 発音中のオペレーター出力レベル変更
- アクティブボイスへのパラメーター反映
- エンベロープの再初期化を避ける方法

Dexed全体はGPL-3.0だが、MSFA由来の部分はApache-2.0とされている。

**ただし、ディレクトリ単位でライセンスを決めつけず、各ファイルのライセンス表記と変更履歴を確認すること。**

### Synth_Dexed / MiniDexed

https://github.com/dcoredump/Synth_Dexed

https://github.com/probonopd/MiniDexed

以下の機能について調査する。

- `doRefreshVoice()`
- リアルタイムパラメーター更新
- アクティブボイスへの設定反映

これらはGPL系の実装なので、**コードをコピー・移植しないこと。**

公開資料から要求仕様や挙動を理解する参考にとどめる。

## 3. ライセンス方針

最重要条件：

**TetoricaのMSFA部分はApache-2.0を維持する。**

以下を守ること。

1. Google MSFAのApache-2.0コードをベースにする。
2. Dexedのコードを利用する場合、該当部分のライセンスを確認する。
3. GPL-2.0 / GPL-3.0コードをコピーしない。
4. ライセンスが不明なコードを取り込まない。
5. 必要な機能はApache-2.0のコードを基に独自実装する。
6. 既存の著作権表示とライセンス表記を維持する。
7. 必要な変更履歴とNOTICEを記録する。

ライセンス判断に不確実性がある場合は、実装を進めず報告すること。

## 4. 実装する機能

### Phase 1：オペレーター出力レベル

最初に、発音中のオペレーター出力レベル変更を実現する。

概念的な使用例：

```javascript
dx7.noteOn(60, 100);

await tween(1000, (t) => {
  dx7.setOperator(2, {
    outputLevel: Math.round(99 * t),
  });
});

dx7.noteOff(60);
```

要求：

- Note On後の変更が発音中のボイスに反映される
- Note Onを再実行しない
- エンベロープを不必要にリセットしない
- 既存の音色パラメーターとの整合性を維持する
- 複数のアクティブボイスに適切に反映する
- AudioWorkletでリアルタイム動作する

### Phase 2：周波数関連パラメーター

以下を検討・実装する。

- Frequency Ratio
- Fixed Frequency
- Detune

発音中の変更が音に反映されること。

周波数変更時に位相が不必要にリセットされないようにする。

### Phase 3：アルゴリズム・フィードバック

以下を検討する。

- Algorithm（32種類）
- Feedback

発音中のアルゴリズム変更は不連続な波形変化を生む可能性がある。

そのため、既存のボイス状態を保持したまま変更できるか調査する。

クリックノイズ対策が必要な場合は、その方法と処理コストを報告する。

**アルゴリズム変更は、Phase 1・2と分離して実装してよい。**

### Phase 4：エンベロープ

以下のリアルタイム変更を検討する。

- EG Rate
- EG Level
- Rate Scaling
- Output Level

特に、発音中にEGパラメーターを変更した場合の挙動を定義する。

原則として、現在のエンベロープ状態を維持しながら、新しいパラメーターを反映する。

ただし、実装上難しい場合は、制約を明示する。

## 5. API設計

既存のDX7 APIを優先する。

新しいAPIが必要な場合も、YM2612との一貫性を重視する。

概念例：

```javascript
dx7.setOperator(2, {
  outputLevel: 80,
});

dx7.setOperators([
  // ...
]);

dx7.setAlgorithm(5);
dx7.setFeedback(3);
```

既存のAPIを破壊しないこと。

また、発音中の変更を反映するためだけに、利用者へ明示的な `refreshVoice()` の呼び出しを要求しない設計を優先する。

## 6. リアルタイム処理

AudioWorklet内での動作を前提とする。

以下を考慮する。

- 音声処理中のメモリアロケーションを抑制する
- 音声処理をブロックしない
- パラメーター変更時のCPU負荷
- 複数ボイスへの更新コスト
- パラメーター変更の反映タイミング
- WASMとJavaScript間の通信コスト

可能であれば、パラメーター変更を音声処理ブロックの境界で安全に適用する。

## 7. テスト

少なくとも以下を検証する。

**基本動作**

- Note On後にOutput Levelを変更すると、発音中の音が変化する
- Note Onを再実行しない
- Note Offが正常に動作する
- 新しいNote Onにも変更後の音色が適用される

**複数ボイス**

- 同時発音中の各ボイスに変更が反映される
- ボイス割り当てが破壊されない
- 発音中のノートが意図せず停止しない

**互換性**

- 既存のDX7プリセットが正常に再生できる
- 変更操作を行わない場合、従来の音声出力と一致する
- 既存のJavaScript APIが正常に動作する

**性能**

- AudioWorkletで音切れが発生しない
- 高頻度のパラメーター変更でも異常終了しない
- CPU使用率の変化を測定する

可能であれば、WAV出力やサンプル比較による自動テストを追加する。

## 9. 作業方針

以下の順番で進める。

1. 既存コードを調査する
2. MSFAとDexedの違いを調べる
3. ライセンスを確認する
4. Phase 1を実装する
5. テストする
6. Phase 2を実装する
7. テストする
8. Phase 3・4の実現可能性を調査する
9. 安全に実装できる範囲を実装する
10. 結果をIssueに記録する

**実装可能な範囲については、途中で逐一確認を求めず、自律的に作業を進めること。**

ただし、以下の場合は作業を停止して報告する。

- GPLコードの取り込みが必要になる場合
- ライセンスが不明な場合
- 既存APIの破壊的変更が必要な場合
- 大幅なアーキテクチャ変更が必要な場合
- 既存の音声再生に重大な影響が出る場合

## 最終目標

MSFAを単なるDX7プリセット再生エンジンではなく、**発音中に6オペレーターFMの音色をプログラムから操作できる音源**へ拡張する。

既存のDX7音色との互換性を維持しながら、Tetoricaの `tween()` や `liveLoop()` からリアルタイムに音色を変更できるようにする。

---

### 補足：今回の優先順位

私なら、まず **Phase 1のOutput Level変更**を確実に完成させます。

これができれば、MSFAのアクティブボイスを更新する仕組みが成立したことになります。

その後、Ratio、Detune、Feedbackへ拡張できます。

アルゴリズムとEGは内部状態への影響が大きいので、無理に一度で完成させる必要はありません。

そして、今回のライセンス条件は重要です。

**Dexedを参考にすることと、DexedのGPLコードを取り込むことは別です。**

なお、GPLコードを読んで独自実装すれば必ずライセンス上問題ない、というわけではありません。実装の類似性や権利関係に注意し、Apache-2.0のコードと公開仕様を基礎に、独立した実装であることを記録する方針にしてください。
